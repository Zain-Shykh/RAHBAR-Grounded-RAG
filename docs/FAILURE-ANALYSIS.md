# Failure analysis

All six stages were broken on purpose, one at a time, on the real stack (Chroma 1.0.12 and Redis Stack in Docker, Ollama with `llama3.2:3b` and `nomic-embed-text`, the 981-chunk index of the real corpus). A, C, E and F were run on 2026-11-05 (spec `docs/specs/phase-13-failure-analysis.md`, D-83), B and D on 2026-11-07 (spec `docs/specs/phase-16-failure-experiments-bd.md`, D-105, D-106). Each break was a local environment variable, an in-memory patch in a throw-away script, or a one-line edit reverted with `git checkout`. Nothing was committed and no default changed. The raw captures of B and D are `docs/evidence/k16-*.txt` (command first, then the output).

**Only stage F is the model's fault.** Stages A to E are ours: extraction, chunking, retrieval, the embedding pin, the prompt and the scope filter. When an answer is wrong, check A to E first (architecture 5.14). The experiments also show that the model stage was the one that did *not* visibly break.

The baseline used for comparison is `eval/baseline.json` (recall@3 = recall@5 0.875, citation validity 1.0, abstention 1.0) and the live index.

## Stage A · Extraction (scanned PDF without OCR)

- **What we broke:** `faculty-entrepreneurship-and-technical-start-ups-policy.pdf` (8 pages, all scanned) was indexed with `pipeline.extract._ocr_page` replaced by a function returning `""`, using the real pipeline (`python -m pipeline.run` style, `indexer/pipeline/run.py`) on a copy of that PDF and the fee page, into a separate collection `rahbar_exp_a` with the same chunk settings (400/50). The live collection was not touched (D-84).
- **Symptom:** the indexer exits with status 0 and stores 7 chunks, all from the fee page. The policy contributes none. The question "What are the eligibility criteria for a faculty member to start a technical start-up?" returns HTTP 200 with `"answered_from_context": false` and the canned "The documents in the corpus do not cover this question.", `X-Outcome: abstained`. The retrieved list holds only `fee-structure-page.html` chunks.
- **Diagnosis, as if we had not caused it:** a user sees an abstention on a question about a document we say we hold. Step 1, the response: `retrieved` has no chunk of that source, and the top scores are low. Step 2, the `answered` log line for that `request_id`: `scores [0.613, 0.5669, 0.5607, 0.5562, 0.5514]`, `outcome: abstained`, all `chunk_ids` from `fee-structure-page`. Step 3, the same line: `"outcome": "abstained"` with the abstain reason `below_floor`, best score 0.613 under the floor 0.70 (the `rahbar_abstentions_total{reason="below_floor"}` and `rahbar_top_score` metrics carry the same fact; they were not captured separately). Step 4, the index: `scripts/check_index.py` lists chunks per source and the policy is missing (40 at baseline); the indexer log has the two lines that name it: `"extracted", "source": "faculty-entrepreneurship-and-technical-start-ups-policy.pdf", "pages": 8, "ocr_pages": 8` and `"document produced no chunks"`. A user cannot see this from the API alone: the answer looks like a legitimate "not in the documents".
- **Stage:** A, extraction (ours).
- **Remedy:** the cause is OCR returning nothing: check the indexer log for `ocr failed` lines (a missing `tesseract` package in the image produces one per page) and fix the image. Then re-run the indexer. To catch it earlier: make the Job fail (non-zero exit) when a document in `corpus/_index.json` yields zero chunks, and have `check_index.py` require at least one chunk per listed source. Today both only log a line (`indexer/pipeline/run.py`), which is the gap this experiment exposed. Not implemented here (no new code in this phase); it is listed as a recommendation.
- **The number:** policy chunks 40 at baseline against 0; `ocr_pages=8` with `chunks=0`; best score for the policy question 0.911 (all five chunks from the policy: "Eligibility criteria for a technical start-up" 0.911, "Evaluation criteria" 0.867, "Scope" 0.794) against 0.613 (five fee-page chunks) without OCR. Same question, same code, same floor; only the extraction changed.

## Stage B · Chunking (100-word chunks, no overlap)

- **What we broke:** the real indexer on the whole corpus (9 documents, 73 051 source words) with `CHUNK_SIZE=100 CHUNK_OVERLAP=0 CHROMA_COLLECTION=rahbar_exp_b` (environment variables only; the live collection `rahbar` was not touched; D-105). The chunker's unit is words (AD-10), so "100 tokens" in the assignment is 100 words here. The chunker still splits on headings, paragraphs and sentences first, so this is the break the configuration can produce, not a blind 100-word window: a section shorter than 100 words stays whole. The indexer took 431 s (`indexer finished`, 1 402 chunks embedded with `nomic-embed-text` in 332 s; `docs/evidence/k16-b-indexer-log.txt`). Evidence: `docs/evidence/k16-b-chunk-stats.txt`, `k16-b-recall.txt`, `k16-b-expect-coverage.txt`, `k16-b-boundary-chunks.txt`, `k16-b-answers.txt`, `k16-b-single-copy.txt`.
- **Symptom:** small. The golden-set recall did not move (recall@3 and recall@5 0.875 on both collections, by type identical: ordinary 0.909, version 1.000, exact 0.500, injection 1.000) because recall is scored on the section heading and the chunker keeps the heading on every piece. What changed is what the chunk contains. Long clauses and lists are cut: 7 mid-sentence cuts in the Rules Handbook and the Student Handbook (chunks of at least 90 words that end without punctuation and are followed by one starting in lower case; the Annual Reports and the 2023 rules were not scanned; the scan output was not saved and `rahbar_exp_b` was deleted, so this count and the cut positions quoted below are not reproducible from `docs/evidence/` without re-running the 431 s indexer; the retrieved text of the boundary questions is in `k16-b-boundary-chunks.txt` and `k16-b-single-copy.txt`); for example `academic-rules-handbook-jun-2026-p052-c249` ends "... should be referenced within the text or content of the assignment and in the" and `p053-c250` starts "reference list."). A stricter metric, "does any of the top 5 chunks contain the golden `expect` text", fell from 14 of 16 to **13 of 16** (q04 "entire assignment" is no longer in the top 5; q09 moved from rank 1 to rank 2). The effect is on enumerations: the Handbook's list of unacceptable uses of Generative AI (6 items, 1 chunk of 370 words at 400/50 (chunk size not saved as evidence)) became 5 chunks; for q04 the real pipeline (`llama3.2:3b`, valid citation, `answered_from_context: true`) answered with the first group only: "using the technology to create assessments that are then claimed as one's own original work", against "6" at 400/50 (which is itself a poor answer; a bare number is the model's habit, see Stage F). Restricted to the Academic Rules Handbook (one copy of the text) the 100/0 answer to the same question was one short sentence covering about three of the items ("Using Generative AI tools to create assessments that are then claimed as one's own, or using them to circumvent requirements, or using them in a way that lacks critical analysis or results in unfair advantage."), against a list of five at 400/50.
- **Where the cut did no harm, and why:** three questions were chosen because the answer sits on a cut: "Where must an AI-generated image or figure be referenced in an assignment?" (the cut falls inside "and in the | reference list"), "Why should students not put their work into generative AI platforms ...?" (cut inside "your work might be | used in another's work") and "Why are students encouraged to go to academic sources ...?" (cut inside "(2) have the sufficient depth | of understanding and critique" (cut position not saved as evidence)). With `TOP_K=5` the neighbouring chunk was usually retrieved as well (single-copy run: ranks 1 and 2 were `p052-c249` and `p053-c250`), and the answer was complete: "Within the text or content of the assignment and in the reference list." With both copies of the text in the corpus (the Rules Handbook and the Student Handbook repeat the section) the answer was the tail only, "in the reference list", cited to the Student Handbook p. 58, which held the whole sentence: the cut chunk took a slot and the model still shortened the answer. For the "Why" question the 100/0 answer was a different true sentence of the same passage ("... sites that do not have clear privacy policies and opt outs") where 400/50 gave "... risking plagiarism"; both are supported by the cited chunk, so this one is not damage from the cut. The third question: 400/50 "academic sources provide fact-checked content and are less likely to reproduce inherent biases", 100/0 "academic sources are considered more reliable and accurate than AI tools"; neither quotes the passage, the cut did not decide it. These are single runs at temperature 0.2 on a 3B model, so some wording differences between the two columns are run-to-run noise (the 400/50 single-copy answer "because it may lead to plagiarism" is a different wording from "... risking plagiarism" in the first run of the same index). Honest count: 1 clear degradation (q04, the list), 1 partial (the figure question, with both copies), 2 no harm that can be attributed to the cut.
- **Diagnosis, as if we had not caused it:** nothing in the golden-set gate moves, which is the point: recall@5 0.875 stays. What shows it, in order: (1) `rahbar_index_info{chunks="1402"}` and the collection metadata `chunk_count 1402, chunk_size 100, chunk_overlap 0` against 981, 400, 50 at baseline (`scripts/check_index.py` prints them); the indexer log line `chunked total ... chunks=1402` and the per-document `chunked` lines (`chunks` 47 for the policy against 40). (2) The size histogram of the stored chunks: at baseline 217 of 981 chunks are over 100 words (up to 400, median 31); in the experiment none (max 100, median 44), and 505 of 1 402 sit in the 76-to-100 bin, a pile-up at the limit that means "cut here". (3) The share of chunks that end without sentence punctuation. (4) In the `answered` log line, `tokens_in` should fall (smaller blocks; not measured here, JSON logging was off) and answers get shorter and incomplete on list questions; request time was 95 to 132 s at 400/50 and 41 to 54 s at 100/0 in the four-question run. A user sees "the answer is only part of the list" and "the quote stops mid-sentence", which looks like a model problem; the retrieved text in the response (`retrieved` and the cited chunk) shows the sentence is cut in the source chunk, so the fault is chunking, not generation.
- **Stage:** B, chunking (ours).
- **Remedy:** keep 400/50 (the chunker keeps clauses and lists together, and the overlap covers the rest). Recommendation only, not built: add the stricter check used here ("the golden `expect` text is inside the top 5") to `eval/retrieval_only.py` so a smaller chunk size shows up as a number, and a metric or log field for the share of chunks that end mid-sentence at index time. If chunks must be smaller, keep a sentence-aware boundary and some overlap, and raise `TOP_K` so the neighbour of a cut chunk is retrieved.
- **The numbers:** 981 chunks (400/50) against 1 402 (100/0), x1.43; chunks over 100 words 217 against 0; median chunk 31 against 44 words; chunks ending in sentence punctuation 69.0% against 76.2% (the smaller chunks end on a section end more often, so this number alone hides the cuts); recall@3 and recall@5 0.875 against 0.875; expect-text in the top 5 14/16 against 13/16 (`k16-b-expect-coverage.txt`); the 6-item list question: 1 chunk against 5.

## Stage C · Retrieval and the embedding pin (`EMBED_MODEL` changed on the API only)

- **What we broke:** the API started with `EMBED_MODEL=hashing-bow-768` while the collection `rahbar` was built with `nomic-embed-text`. The indexer was not changed. `hashing-bow-768` was chosen on purpose: it has the same dimension (768) as `nomic-embed-text`, so the vector store accepts the query without any error. This is the pin demonstration (architecture 5.3, invariant on one embedding model). `TOP_K=1` was not run.
- **Symptom:** `/readyz` returns 503, the pod would be `0/1 READY`, `/api/ask` returns 503 `{"detail":"index unavailable"}`, while `/healthz` still returns 200 `{"status":"alive"}` (it touches no other service), so the pod is not restarted in a loop.
- **Diagnosis, as if we had not caused it:** `kubectl get pods` shows `0/1`; `curl /readyz` gives the body below, which names the failing check; the API log has one ERROR line with both model names. `/metrics` still shows `rahbar_index_info{chunks="981",embed_model="nomic-embed-text",index_id="20261105T102247Z-5a3b5a"} 1.0`, so the pod knows which model built the index. The fix is a config diff: ConfigMap `EMBED_MODEL` on the api against the one on the indexer.
- **Stage:** C, retrieval (ours); the pin is what turned a silent quality failure into a loud one.
- **Remedy:** set the same `EMBED_MODEL` on both (one ConfigMap key), or re-run the indexer with the new model (stage-and-swap, the API becomes ready on the new index without a restart).
- **The numbers (captured):**

`/readyz`, HTTP 503:

```json
{"status":"not_ready","failed":["embed_pin"],"checks":{"chroma":"ok","collection":"ok","embed_pin":"failed","redis":"not_checked","embed_dimension":"not_checked"}}
```

API log line (JSON, stdout):

```json
{"ts": "2026-11-05T15:32:53Z", "level": "ERROR", "logger": "rahbar.index_state", "msg": "embedding pin conflict", "request_id": "-", "collection_embed_model": "nomic-embed-text", "api_embed_model": "hashing-bow-768", "collection": "rahbar", "action": "not ready until the indexer re-runs with the same model"}
```

  What the pin prevented: with the check bypassed (a script calling Chroma directly with the 768-dimension hashing vector), the query "Are mobile phones and smart watches allowed in the examination hall?" raises no error and returns these best matches: score 0.045 `academic-rules-handbook` "Shah Latif Town (on National Highway)", 0.039 "5.20 Application to recheck a final exam", 0.038 `fee-structure-page` "Miscellaneous Fees", 0.035 and 0.034 address chunks. With the right model the same question gives 0.908 "1. Mobile Phones, Smart Watches and all electronic" in the Student Handbook. Same dimension, no error, completely wrong neighbours: recall would be 0 and the only visible symptom would be abstentions (every score under the floor) or, with a low floor, nonsense context.

## Stage D · Prompt (the "use only the evidence" instruction removed)

- **What we broke:** a throw-away script (not in the repo; D-106) sets `app.services.prompt.SYSTEM` in memory and calls the real `answer_question` (retrieval, floor, `llama3.2:3b` through the Ollama provider, validator, one retry), collection `rahbar` (400/50), `cache=None`, Redis flushed, defaults otherwise (`TOP_K=5`, floor 0.70, `TEMPERATURE=0.2`). Two variants, each printed at the top of its evidence file: **D1** removes the sentence "Use ONLY the evidence blocks in the user message." (the literal requirement); **D2** also removes "If the evidence does not answer the question, set answered_from_context to false, say the documents do not cover it, and cite nothing." The schema, the citation validator and the floor are unchanged. Twelve questions, one run each, same questions for all three prompts: 3 in-corpus, 5 out-of-corpus whose retrieval still passes the floor 0.70 (found with `eval/retrieval_only.py ask`: top 0.708 to 0.766), 3 general-knowledge questions whose retrieval passes the floor (0.72 to 0.81), 1 general-knowledge question below the floor. Evidence: `docs/evidence/k16-d-intact.txt`, `k16-d-d1.txt`, `k16-d-d2.txt`, `k16-d-cited-chunks.txt`, `k16-d-d2-fallback-log.txt`, `k16-d-golden-abstain-*.txt`.
- **Symptom:** D1 shows **no move toward the model's own knowledge**. Out-of-corpus questions kept abstaining ("The documents do not cover the grading scale used at Harvard University"); the 3B model with the `answered_from_context` field in the schema keeps the abstain habit on its own. D1 did show noise: the mobile-phone question (in the corpus, top 0.908) came back as `abstained` with the answer text "false", where the intact prompt answered "No". One run each at temperature 0.2, so this may be run-to-run variance; it is reported, not explained. **D2 degrades visibly, in four ways:**
  1. *Outside knowledge inside a "from context" answer.* "What is the difference between a semester and a trimester system in universities?" (retrieval top 0.722, the Rules Handbook's semester clause): the intact and D1 runs abstained; the D2 run in `k16-d-d2.txt` ended in the canned fallback (`outcome: fallback`), and a second D2 run (`k16-d-d2-fallback-log.txt`, JSON log on) logged `model output rejected ... bad_citation: student-handbook-jun-2026.pdf / VI – SEMESTER RULES` (attempt 1, will retry) and then **answered**: "The university uses a semester system, with two regular semesters in an academic year, whereas a trimester system typically consists of three equal-length terms.", `answered_from_context: true`, one valid citation (Rules Handbook 1.3, p. 6). The second half is not in the corpus. The fallback in one run and the answer in the other is the same question, so the model is unstable here; the one-retry path did its job (a rejected citation is retried, never a 500).
  2. *A number not in the cited text.* "How many credit hours does a typical American bachelor's degree require?" (top 0.766): intact and D1 abstained; D2 answered **"120"** with `answered_from_context: true` and a citation to Rules Handbook 1.12. The cited chunk (and the Prospectus chunk ranked first) contain no 120, and no chunk of the live collection has 120 near "credit" (`docs/evidence/k16-d-cited-chunks.txt`). The citation is valid (it matches a retrieved chunk), the content is from the model's training. This is the case the validator cannot catch: it checks that a citation was retrieved, not that the answer is in it.
  3. *An abstention that is flagged as an answer.* "What is the grading scale used at Harvard University?" (top 0.727): D2 returned `outcome: answered`, `answered_from_context: true`, with the text "There is no information provided about the grading scale used at Harvard University in the given evidence." `cacheable()` accepts it (outcome `answered`, from context, a citation that was retrieved), so it would be stored and served from the semantic cache until the TTL; a UI that trusts the flag shows an answer badge on a refusal.
  4. *In-corpus answers shifted.* Generative AI unacceptable uses: intact four items, D1 one item, D2 three items; mobile phones: D2 "No mobile phones and smart watches are allowed in the examination hall." (a full sentence, as the system prompt's remaining line asks) against "No" intact.

  Counts over the 8 questions about things the corpus does not answer (questions 4 to 11 in the order of the evidence files, the three in-corpus ones first and "capital of France" last; the NUST question is counted in every column and is not a D effect: the model gave the Prospectus clause "Minimum attendance requirement for Undergraduate degree programs are 80%", the cited chunk `prospectus-2026-academic-rules-and-regulations-p001-c001`, as the answer for NUST): `answered_from_context: true` intact 2 of 8 (NUST, founder), D1 2 of 8, D2 5 of 8 in the main run (Harvard, NUST, American, founder, GPA) and 6 of 8 counting the trimester rerun. Read that count with care: of the extra "true" answers in D2, only "120" (and the trimester rerun) is outside knowledge; Harvard is a refusal flagged as an answer; GPA is grounded (the corpus defines SGPA and CGPA). So the clean D2 damage is two outside-knowledge answers, one mislabelled refusal and the loss of two abstentions, out of 8. Retries were not captured in the main runs (JSON logging was off); the final outcome `fallback` occurred 0 times (intact), 0 (D1) and once (D2, the trimester question), and the D2 rerun with logging on shows one `bad_citation` retry before an answer. The "founder" answer ("founded ... by Dr Ayub Alvi") is the same in intact and D1: the cited Annual Report preamble (`annual-report-2019-20-p003-c004`, excerpt in `k16-d-cited-chunks.txt`) says "Founded as a Federally Chartered University in July 2000" and names Dr Ayub Alvi, as far as the saved search shows, only as the signing Rector; D2 dropped the person ("FAST-NUCES was founded in July 2000"). The injection golden question q18 held in the intact and D2 runs (the answer says 100% attendance; D2 flipped `outcome` from `abstained` to `answered` with the same content; the intact run's `abstained` outcome with a correct answer text is itself an inconsistency of the baseline); D1 was not run on q18. The two must-abstain golden questions (hostel, q16 and q17) are **below the floor** (0.655, 0.658), so no model call is made and D2 cannot change them: abstention stayed 1.0 under D2 (`k16-d-golden-abstain-d2.txt`), which is why the golden-set gate would not have noticed this break.
- **Diagnosis, as if we had not caused it:** nothing in the committed gate moves (abstention correctness 1.0, citation validity 1.0, recall unchanged), because the golden must-abstain questions never reach the model. What would show it: (1) `rahbar_abstentions_total{reason="model"}` falling toward 0 while `rahbar_abstentions_total{reason="below_floor"}` stays flat: the model stopped saying "not covered" on questions whose retrieval passes the floor; (2) the `answered` log line with `outcome: answered` and a lowish `scores[0]` (0.72 to 0.77 here; questions the corpus answers ranged from 0.71 to 0.91 in the golden set, so this is a weak signal on its own), and a rise of `rahbar_fallbacks_total{reason="bad_citation"}` when the model cites a block it did not use; (3) a spot check of the cited chunk text against the answer: a number or a clause in the answer that the chunk does not contain (the "120" case). A user would see confident answers about other universities and about general topics, with a FAST-NUCES citation attached. The cause is the generation stage's input, not the model: the prompt text is in `api/app/services/prompt.py` and in the request the provider logs, so `git diff` on `prompt.py` (or a hash of `SYSTEM` logged at start-up, which we do not do today) shows it at once; a model change would not show a prompt diff.
- **Stage:** D, prompt (ours). The model did the visible damage, but it is the prompt that removed its brakes; the fault is in our instruction, so it is not stage F.
- **Remedy:** restore the instruction (it is one constant, `SYSTEM`). No test pins its wording today: `api/tests/test_prompt_validate.py:35` only checks that the first message equals `SYSTEM`, so deleting the sentence would pass `make test`. Recommendations only, not built: (0) one assertion that `SYSTEM` contains "Use ONLY the evidence blocks" and the abstain rule; (a) add two or three out-of-corpus golden questions whose retrieval passes the floor (for example "What is the grading scale used at Harvard University?", top 0.727, abstains at baseline) so the gate sees a prompt regression; (b) a cheap grounding check after validation: numbers and capitalised names in the answer must appear in the cited chunk text, else treat as `invalid_output` (it would have caught "120"); (c) treat an `answered_from_context: true` answer whose text says "no information" as an abstention. The floor stays the first defence: it kept "capital of France" at 0.572 with no model call in all three prompts (0.1 s intact and D1; 6.5 s in D2, retrieval only, on a loaded laptop).
- **The numbers:** answered_from_context true on the 8 out-of-corpus-or-knowledge questions: 2 (intact), 2 (D1), 5 (D2, 6 with the rerun); a figure not in the cited chunk: 0, 0, 1 ("120"); a flagged answer whose text says there is no information: 0, 0, 1 (Harvard); final fallbacks: 0, 0, 1; golden abstention under D2: 1.0 (floor-protected); latency of the successful model calls unchanged in kind (15 to 140 s on CPU, with two D2 calls at 328 s and 438 s when the laptop was loaded, not attributable to the prompt).

## Stage E · Source scope (the `superseded` filter removed)

- **What we broke:** in `api/app/services/scope.py`, the default scope `Scope({"superseded": False}, "current")` was changed to `Scope(None, "current")` (a one-line local edit, reverted with `git checkout`). The API was then restarted and asked the version-sensitive question "What is the deadline to withdraw from a course?" (golden q12). The August 2023 rules say "last day of classes"; the June 2026 Handbook says "last day of the makeup week of every semester".
- **Symptom:** the superseded 2023 clause is the best match and goes into the prompt. Real run, `llama3.2:3b`, cache flushed, 48.8 s: the model **still answered with the 2026 rule** ("The deadline to withdraw from a course is the last day of the makeup week of every semester.", citing the 2026 Handbook 4.25 and 6.8), `answered_from_context: true`, valid citations. So on this question the model absorbed the damage; the stale clause was a latent risk, not a wrong answer. Nothing in the output says so.
- **Diagnosis, as if we had not caused it:** the answer looks correct, so there is no user-visible symptom here. What shows it is the `answered` log line: `"scope": "current"` but `chunk_ids` starting with `undergraduate-academic-rules-aug-2023-p016-c095`, a source that must never appear under `current`. Recall by type does not show it: version-type recall@5 stayed 1.000 and overall recall@5 stayed 0.875 with the filter removed (`eval/retrieval_only.py recall` run under the broken scope; both versions are in the top 5). The check that would is "superseded chunks in the top 5 for a `current` scope", which is not a metric today; the retrieval-only contamination count below is how it was measured.
- **Stage:** E, source selection (ours).
- **Remedy:** restore the filter (it lives in one function, `scope()`, unit-tested in `api/tests`). Add a guard test or a metric counting retrieved passages with `superseded=true` under a `current` scope; it must be 0.
- **The numbers:** top 5 for q12 with the filter: 0.895 Handbook 4.25 first, no 2023 chunk. Without it: 0.896 `undergraduate-academic-rules-aug-2023` 4.25 first, 0.895 Handbook 4.25 second (a 0.001 difference decides the order). Across the golden set under the broken scope, 9 of the 15 questions with `current` scope had at least one superseded chunk in the top 5 (q01 ranks 4 and 5, q02 ranks 2 and 3, q03, q05, q07, q08, q12 rank 1, q15, q18); after the revert 0 of 15 (q13 asks for 2023 on purpose and is allowed). In the `answered` line: `"chunk_ids": ["undergraduate-academic-rules-aug-2023-p016-c095", "academic-rules-handbook-jun-2026-p023-c124", ...]`, `"scores": [0.8956, 0.895, ...]`.

## Stage F · Generation (`TEMPERATURE=1.2`)

- **What we broke:** the API started with `TEMPERATURE=1.2` (default 0.2), cache flushed, four uncached golden questions asked one at a time (q06, q07, q03, q04), then the same four at the default 0.2 for comparison.
- **Symptom:** on this model, at this sample size, **none that matters**. 4 of 4 answered with valid citations; zero retries (`will retry` appears 0 times in the log), `fallback_reason` is null on all four `answered` lines (the `rahbar_fallbacks_total` metric was not captured), no abstention. The structured output (`format=<Answer schema>`) kept the JSON valid even at 1.2. What changed is wording and length: q04 ("what counts as unacceptable use of Generative AI") came back as a full clause at 1.2 ("using Generative AI tools to circumvent the requirements of an assessment or create assessments that they then claim as their own original work.") against "1, 2, 6, 7, 8" at 0.2. Output tokens: 106, 110, 97, 364 at 1.2 against 164, 108, 103, 292 at 0.2, no consistent direction. Request seconds 25.0, 38.8, 30.6, 150.8 at 1.2 against 34.1, 15.2, 13.2, 56.1 at 0.2; the second run came right after the first, so the model was already loaded; this difference is not attributable to temperature.
- **Diagnosis, as if we had not caused it:** if temperature drift were hurting answers, it would show in `rahbar_fallbacks_total{reason="invalid_output"|"bad_citation"}` (retries and canned responses), in the `rahbar_tokens{direction="out"}` histogram shifting upward, and in the golden-set citation validity falling below 1.0 in `eval/run_eval.py`. None of the three moved in this run. The honest conclusion is that four questions cannot show a real degradation; the claim of the architecture (5.14: validation failures, rambling) is a risk, not something we reproduced.
- **Stage:** F, generation. The only stage that is the model's fault, and the only one in which we could not make it break.
- **Remedy:** keep `TEMPERATURE=0.2` (facts and JSON want a low value, not 0, so the one retry can differ; H-7). Watch the three signals above after any change of model or temperature, and run the golden set before shipping it.
- **A side finding:** the semantic cache key is the question embedding and the scope tag. It does not contain `TEMPERATURE`, `TOP_K` or the code of the scope function. Answers produced under a bad setting stay served until the TTL (86 400 s) or a re-index.
